# Decision 02 — BNO085 IMU

## What the source confirms

- I²C device at address `0x4A << 1 = 0x94` (`bno085.h:9`).
- SHTP protocol over I²C (`bno085.c:9-53`).
- Three reports enabled at 100 Hz each (`freertos.c:117, 119, 121`):
  - `BNO085_REPORT_ROTATION_VECTOR` (0x05, mag-fused 9-DoF)
  - `BNO085_REPORT_ACCELEROMETER` (0x01)
  - `BNO085_REPORT_GYROSCOPE` (0x02)
- INTN pin on PB4 with falling-edge EXTI (`gpio.c:64-68`).
- Quaternion components in Q14 fixed-point, accuracy in Q12 (`bno085.c:182-185, 217-228`).

## What the BNO085 brings to the system

- **Onboard 9-DoF fusion.** Outputs a directly usable quaternion. The STM32 does not run its own fusion math — just packet decoding + bias compensation.
- **Sensor accuracy field.** The 0x05 Rotation Vector includes a per-frame accuracy estimate (Q12 radians). Read into `dev->data.quat_accuracy` (`bno085.c:228`) — currently unused downstream.
- **I²C interface.** Simple two-wire connection; no SPI / SDIO needed.
- **INTN pin.** Allows event-driven reads instead of polling (used via EXTI4).

## Why this choice fits the firmware

A new engineer should understand: the team's firmware is largely a **BNO085 SHTP driver + actuation passthrough**. The BNO085's onboard fusion delivers a quaternion that the Jetson EKF can consume directly. The STM32 doesn't need to know about magnetometers, accelerometer noise models, or Madgwick filters — that complexity is encapsulated in the chip.

## Alternatives the choice rules out

- **BNO055** (predecessor): also has onboard fusion but lower performance and different SHTP/UART protocol. Drop-in replacement is non-trivial because the report formats differ.
- **Raw 6-axis IMU (MPU6500, ICM-20948, etc.):** would require implementing a fusion filter on the STM32 — Madgwick or Mahony at minimum. That code does not exist in this firmware; building it would substantially expand the SHTP-walker-sized driver into a real EKF.
- **Bosch BMI270 + BMM150 (separate accel/gyro and mag):** more flexibility but more parts + integration complexity.

## What the current code does NOT use

The header `bno085.h:101-109` declares but does not implement:
- `BNO085_ConfigCalibration` — controls per-axis calibration enable.
- `BNO085_SetDCDAutoSave` — periodic DCD (Dynamic Calibration Data) save.
- `BNO085_SaveDCD` — one-shot save.
- `BNO085_DisableDynamicCalibration` — turn off the DCD loop.

These exist as headers without bodies. Calling them would produce a linker error. They represent an intent that the current implementation does not realise. **This is a known gap** (see `bno085/04_report_configuration.md` §"Dynamic Calibration (DCD) management").

## Drawbacks visible in current source

- **EMI vulnerability of magnetometer.** The Rotation Vector report (0x05) is 9-DoF mag-fused. Under BLDC motor EMI, the magnetometer contribution to the fused quaternion can be corrupted. The firmware mitigates by:
  - Publishing wider yaw covariance (`0.01 rad²`, `freertos.c:238`).
  - Quaternion sanity gate `|q|² ∈ [0.9, 1.1]` (`bno085.c:193, 223`) dropping wildly-corrupted samples.
- **No hardware reset path.** nRESET is not wired to STM32 — a wedged BNO085 cannot be hardware-reset by firmware. Only power-cycle the vehicle, or rely on IWDG (currently disabled — the IWDG-disabled state).
- **DCD not persisted.** Each boot starts fresh; bias is re-estimated in the 2 s calibration window. NVRAM persistence would speed warm restarts.

## What a future redesign might pick

- **Stay on BNO085, implement DCD persistence.** Save calibration to a small region of FLASH; restore on warm boot.
- **Wire nRESET to a spare STM32 GPIO** so auto-recovery can hardware-reset the BNO085 when bus-stuck.
- **Add a redundant secondary IMU** (e.g., the cheap ICM-20948 — different chip, same I²C bus, separate address) for cross-checking. Triple-modular-redundancy is overkill at this scale; one backup is reasonable.

## What this decision constrains in current code

- Every reference to a Q-point conversion (`bno085.c:59-62`) follows BNO085 SH-2 conventions.
- The SHTP multi-report walker (`bno085.c:115-253`) is BNO085-specific.
- Two-stage I²C read (`bno085.c:9-31`) is SHTP-specific.
- The boot calibration's baseline-quaternion pre-conjugation (`bno085.c:431-434`) is meaningful only when working with unit quaternions — BNO085 always emits these.

Switching IMU would require rewriting the SHTP path entirely.
