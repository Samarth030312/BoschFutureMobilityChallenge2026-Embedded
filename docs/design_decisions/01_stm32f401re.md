# Decision 01 — STM32F401RE as the embedded MCU

## What the source confirms

- Target: `-DSTM32F401xE` build flag (`Makefile:101`).
- Linker config: 96 KiB RAM + 512 KiB FLASH (`STM32F401RETX_FLASH.ld:46-49`).
- Cortex-M4F core: `-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard` (`Makefile:92-95`).
- Single-precision FPU enabled (used by BNO085 quaternion math).
- 84 MHz max clock used (`main.c:188-191`).
- Nucleo board: PA5 is the on-board user LED (`gpio.c:50`), PA2/PA3 are ST-LINK USB-CDC bridge USART2.

## Why this MCU works for this firmware

The current firmware fills the F401RE's resources as follows:

| Resource | Need | Used |
|---|---|---|
| Cortex-M4 + FPU | BNO085 quaternion math (Hamilton products at 100 Hz) | Yes — see `bno085.h:114-123` |
| I²C peripheral | BNO085 SHTP transport | I²C1 (`i2c.c`) |
| UART peripheral | micro-ROS XRCE-DDS link | USART2 @ 460800 (`usart.c:75`) |
| Timer with PWM | Servo + ESC control | TIM2 CH1/CH2 (`tim.c:69-80`) |
| EXTI | BNO085 INTN | EXTI4 on PB4 (`gpio.c:64-74`) |
| 96 KiB RAM | Two heaps × 32 KB + 12 KB task stack + statics | Tight but fits (~97 % used per `it_transport.c:28` comment; the dual-heap sizing) |
| 512 KiB FLASH | HAL + FreeRTOS + micro-ROS static lib + app | Comfortable |

## Alternatives the choice rules out

A larger STM32 (F411, F446, F7, H7) would offer:
- More RAM (could split the dual-heap collision differently).
- Higher clock (saves cycles but isn't needed for the 100 Hz publish rate).
- More peripherals (e.g., CAN — could replace USART for a wider robotics ecosystem).

A smaller STM32 (F0, L0) would NOT work:
- No FPU → BNO085 quaternion math becomes a software-emulation bottleneck.
- Less RAM → couldn't host the dual heap.

## Drawbacks of staying on F401RE

- **RAM-constrained.** the dual-heap sizing dual-heap collision uses 64 KB of 96 KB. Adding another task or sensor pushes against the limit.
- **HSI clock at 84 MHz** has ±1 % accuracy at room temperature . UART baud rate accuracy is at the edge under temperature drift. An external HSE crystal would help but the Nucleo's HSE-via-ST-LINK-MCO requires reconfig.

## What a future redesign might pick

- **STM32F411RE**: same pinout, same Nucleo board, 100 KB more RAM, slightly higher clock. Drop-in replacement.
- **STM32H7**: significantly more capable but very different ecosystem; large complexity jump.
- **CAN-equipped variant** (F446, etc.) if the team ever standardizes on CAN for sensor/actuator buses.

## What this decision constrains in the current code

- Hard-float ABI is locked in (`Makefile:94`).
- FreeRTOS port: `Middlewares/Third_Party/FreeRTOS/Source/portable/GCC/ARM_CM4F/port.c` (`Makefile:66`).
- HAL: `Drivers/STM32F4xx_HAL_Driver/` is F4-family-specific.
- Startup file: `Core/Startup/startup_stm32f401retx.s` (F401-specific vector table).

A migration to a different STM32 family changes all four.
